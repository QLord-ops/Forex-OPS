# Заказчики и линии, разбор Auftrag по заказчику, уверенность по полям, интерфейс DE/EN

План согласован с владельцем 08.11.2026, не начат. Сохранён из рабочего плана Claude Code, чтобы не потерять.

## Context
Владелец (08.11.2026): у Forex несколько заказчиков — Schnellecke, Walter (Tesla), дальше будут ещё. У каждого свой Auftrag и свой порядок работы, у каждого диспетчера свои линии. Цель на будущее — программа, пригодная для любого перевозчика такого профиля.

Решения владельца:
- данные делим **по заказчикам внутри Forex** (не мультиарендность перевозчиков);
- структура **«заказчик → линии»**: машины и диспетчеры привязаны к линиям, категория — метка заказчика;
- диспетчер **видит всё, по умолчанию свои линии**;
- язык интерфейса (ru / de / en) **хранится в учётной записи**, на нём же ИИ пишет предупреждения.

Что сейчас (разведка кода):
- `Vehicle.line` — строка `SCHNELLECKE | WALTER_TESLA | OTHER`, `statusGroup` — `NORD | SUED | LUFE`. Это фактически линии Schnellecke, но в коде.
- Список 07:00 жёстко на `STATUS_LINE = 'SCHNELLECKE'` (`daily-status.ts`). Исключения 727/2853 и колонка «WE in Northeim» тоже в коде (`vehicle-status-settings.ts`, `daily-status-export.ts`, `StatusPage.tsx`).
- У тура нет заказчика. Правила разбора Schnellecke зашиты в промпт (`pdf-order-import.ts` `TOUR_REMARKS_ROUTE_RULE`, `APPOINTMENT_RULE`, `BUILT_IN_IMPORT_RULES`). `ImportRule`, `ImportCorrection` и примеры для ИИ — общие на всех.
- `confidence` есть только на точку и в интерфейсе не показывается. Предупреждения — общий список, не привязаны к полю. (Частично сделано позже: серверная оценка полей `field-confidence.ts`, PR #84.)
- i18n нет. В вебе около 1 600 русских строк в 66 файлах, в API — около 620. Промпты ИИ требуют русский. Все e2e проверяют русский текст.

Порядок: **6 PR**, каждый после «да». PR 1 — миграция (backup + «да»). Переводы (PR 5–6) не зависят от заказчиков и могут идти параллельно, отдельной сессией.

Частично реализовано до начала плана: автоопределение заказчика по шапке/Abteilung (`customer-resolver.ts`, PR #80).

## PR 1 — миграция `customers_lines_locale` (отдельный PR, backup)
Только добавления, старые поля не удаляются (`Vehicle.line` / `statusGroup` остаются до перехода).

- **Customer** — `id, name, slug @unique, category (OEM_LOGISTICS | WAREHOUSE | SPOT | OTHER), aliasesJson, color, active, profileJson, createdAt, updatedAt`. `slug` у Schnellecke = `SCHNELLECKE` — сохраняет историю `DailyStatusReport(line, date)`.
- **CustomerLine** — `id, customerId, code, name, departmentCompany / departmentAddress / departmentCity, sortIndex, active`, `@@unique([customerId, code])`.

- `Vehicle.customerLineId?` (SetNull). `Tour.customerId?`, `Tour.customerLineId?`. `OrderDocument.customerId?`, `ImportCorrection.customerId?`.

- Зеркало SQLite, `modelOrder` в `import-sqlite.mjs`, тест схемы.
- **Перенос данных — не SQL в миграции**, а кнопка админа «Создать заказчиков из линий» (PR 2) с предпросмотром. Аудит.

## PR 2 — заказчики, линии, профили (API + UI)
- Сервис `services/customers.ts`, маршруты `routes/customers.ts`: список, карточка, создать/архивировать — admin; профиль — admin и диспетчеры линий заказчика; линии CRUD; назначение диспетчеров и машин. Zod, роли, аудит.
- Профиль заказчика (`profileJson`, Zod-схема с версией): `import` (где маршрут, слова склада, перевозчик, «дата без времени = 06:00», Zuladung, заметки для ИИ), `statusList` (включён, время, исключённые машины, доп. колонки), `defaults` (стоянка, радиус прибытия). Шаблон «OEM-логистика с Tourbemerkung» = правила Schnellecke.
- Список 07:00 по заказчикам: `DailyStatusService` по заказчикам со включённым `statusList`, группы = линии. Страница «Статус» — вкладка на заказчика. Убрать `STATUS_LINE`, `SCHNELLECKE_PRESET_EXCLUDED`, `GROUP_LABEL`.
- Диспозиция: «Мои» = машины моих линий + лично взятые; чипы «Заказчик» и «Линия»; цветная метка. Уведомления — мои линии + свободные. Туры и история — фильтр по заказчику.
- Web: страница «Заказчики» (список, карточка-профиль с вкладками), на «Машинах» выбор линии, в «Диспетчерах» линии диспетчера. Обзор профиля: машины, туры, Auftrag, доля разобранных без правок, частые правки, правила, документы.
- Тесты: сервис и роли, перенос из линий, статус 07:00 для двух заказчиков, e2e фильтр и создание линии.

## PR 3 — разбор Auftrag по заказчику
- Выбор заказчика при загрузке (по умолчанию — линия диспетчера/машины, иначе автоопределение).
- Автоопределение (`customer-resolver.ts`): псевдонимы, шапка, Abteilung, госномер → линия; ИИ получает карточки заказчиков и возвращает `customerKey`.
- Полный профиль в промпте + 3 последних подтверждённых Auftrag этого заказчика как примеры.
- Смена заказчика в проверке → `POST /documents/:id/reparse`.
- Обучение по заказчику: `ImportCorrection.customerId`, `ImportRule.scope`, встроенные MB/VW/LG — `global`; правило у двух заказчиков → предложить общим.
- Сохранение `Tour.customerId`, `customerLineId`, `OrderDocument.customerId`.
- Перенос Schnellecke-правил из кода в `profilePromptBlock(profile)`; общий синтаксис маршрута остаётся в коде.
- Тесты: определение заказчика, профиль в запросе к ИИ, изоляция правил, примеры только своего заказчика, reparse.

## PR 4 — уверенность по каждому полю
- Поля точки и Auftrag; ИИ возвращает `{ c, evidence }` (пересмотреть: после PR #84 оценка считается на сервере без ИИ).
- Сервер `field-confidence.ts`: основа — оценка; `NO_EVIDENCE` → потолок 0,6; `FORMAT` (адрес без дома/индекса 0,5, дата невалидна 0,3, индекс ≠ город 0,5); происхождение (правило/адресная книга ≥ 0,95, заглушка Tourbemerkung 0,4, из примечания другой точки 0,55, склад Abteilung 0,9); сверка с Tourbemerkung; история правок заказчика; геокодирование «только город» → 0,5.
- Уровни: ≥ 0,85 без пометки; 0,6–0,85 жёлтое «проверьте»; < 0,6 красное с причиной. Предупреждения с `stopIndex` и `field`.
- UI: рамка и причина у поля, сводка сверху, красное блокирует «Подтвердить» до исправления или «Верно».
- Калибровка: при подтверждении сохраняется, какие поля правили; в профиле — точность по уровням.
- Тесты: каждое правило, уровни, привязка предупреждений, e2e блокировки.
